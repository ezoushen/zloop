Load alongside the current host adapter when a `t3` route is selected. T3 Code
(https://github.com/pingdotgg/t3code) provides a transport: it launches and hosts
the worker; it does not replace the Claude, Codex, Pi or OpenCode host identity.
Read the installed `t3` CLI's help (`t3 thread start --help`, `t3 thread send
--help`, `t3 thread show --help`) before the first launch; it owns command
syntax. This file owns zloop coordination.

## Route before launching

Use the configured route; environment presence alone does not select T3. Inspect
readiness and generated delegation fields with:

```sh
python3 <plugin_root>/scripts/t3_preflight.py --project <repo> --execution <execution.json>
```

The saved route supplies a linked environment and its job's write scope. Without a
route, use `--environment <id> --writes <scope>`. `--diagnose` performs read-only diagnostics. Follow a
refusal's named layer; do not repair or restart the user's service to force a launch.

T3 can host the runtimes it supports among zloop's worker runtimes; a model
binding's `id` must be a model that provider accepts, and an unsupported
combination is refused with its reason. Do not infer support from a model name.
Model-only launches need no MCP connection. Explicit thinking settings need T3's
MCP configuration tools to apply and read back the selected level before work.

T3 marks a session it hosts: every provider's carries `T3CODE_CLI_PATH`, Claude's
and Codex's also their own thread id in `T3CODE_THREAD_ID`, and Pi's `T3_MCP_URL`,
`T3_MCP_BEARER_TOKEN`, `T3_PI_RUNTIME_MODE` and `T3_PI_MCP_EXTENSION_PATH` (the
spawner strips inherited values, so presence means this session's own
credentials). Never log the bearer token.

Pass the destination's host adapter to a cross-framework worker, plus this
guide. Use absolute paths for the adapter, agent and job files and verify their
reads succeeded before productive work.

## Start each worker in a thread of its own

1. Start the worker's thread with a fixed startup-only probe, titled
   `zloop/<slug>/<assignment> <role>`. An orchestrator T3 hosts starts it as a child
   of its own thread: `delegate_task` with the probe as `task`, following the wait
   instructions it returns. Only an orchestrator outside T3 runs `t3 thread start
   <project-path> <probe> --title <title> --json`, in the project that contains the
   assigned worktree; that makes a top-level thread.
   After the probe settles, register before submitting the productive packet with
   `t3 thread send`, which queues behind a busy turn and never interrupts. Adding
   `--worktree <base-branch>` (for a child, `isolation: "worktree"`) makes T3 give
   the thread a worktree of its own; a
   read-only assignment runs in the project folder. The thread never runs in a
   zloop-assigned worktree path: the assigned worktree's identity is recorded in
   the registration and verified from the worker's report, not from the thread's
   directory. A new thread uses the project's default model and permission
   mode: verify the project's defaults allow unattended work at the assignment's
   scope before launching, and report a mismatch instead of proceeding.
2. Use the inspector's `launch_arguments` for a hosted local child, adding the
   startup probe as `task`. Outside T3 use the installed CLI's corresponding
   provider/model flags. Do not approximate rejected model slugs. Explicit thinking
   requires configuration/readback support before productive submission; otherwise
   report the missing capability.
3. Register the returned thread ID through [worker attempts](../runtime/workers/prepare.md)
   before submitting productive work. Resolve inspection or lifecycle gaps against
   the same thread rather than starting replacements blindly.

## Wait and recover

Register the attempt with `runtime: "t3"` and the thread id as `native_session`
(the identity is the thread, not a provider session record). At startup, write
`t3 thread show <thread> --json --messages 1000` (the default prints the latest
10, which can drop the packet) to a file and record it as the attempt's
`native` record; **rewrite that file before collection** so the lifecycle reads
the settled status and the packet's reply from the current thread state.
When thinking was selected, also read `t3_thread_configure` for that thread and keep
its returned object under `configuration` beside `thread` and `messages` in the
native record. Refresh both reads before collection. The lifecycle checks the
configuration's thread, provider and model before taking its option as effort.

Bind the prompt, independent wait and collected result to the registered attempt
under [worker attempts](../runtime/workers/prepare.md) and
[waits](../runtime/workers/wait.md). Submit with
`t3 thread send <thread> <packet-text>`, whose text must be the registered
packet; it returns once T3 starts the turn, and `submit` refuses `--wait`.
Acknowledge its receipt, record `reconciled`, then arm `watch` on
`python3 <plugin root>/scripts/native_wait.py t3 <thread>`: it exits 0 once the
turn completed, 1 with T3's answer when it ended another way or the agent
waits for an answer in the app, the orchestrator's choice. For a thread on a
linked environment pass the same two commands: the lifecycle runs the send and
the wait's reads through that environment's MCP server.

T3 hands a child's result to its parent, so a hosted orchestrator's `notify`
only records the receipt (`["echo", "{receipt}"]`). On a wake read the worker's
reply whole with `t3_thread_read`, or a result T3 holds queued arrives as
another turn. A linked environment's thread is nobody's child, so there `notify`
must wake the orchestrator (hosted by T3: `t3 thread send <own thread> {receipt}`,
the `threadId` `t3_thread_configure` answers with no arguments).

After a timeout or failed wait, inspect the same thread with `t3 thread show
<thread> --json` and the lifecycle's `status` command before waiting again or
resubmitting. A timeout is not completion; a duplicate send queues a second turn.

## Sandbox stance and session identity

T3 spawns the provider itself, so zloop cannot wrap the worker's argv: a
T3-hosted worker runs under its provider's own defaults, unenforced by zloop
(the resolver's preflight and the thread's runtime mode are the controls). The
macOS Seatbelt profiles apply to the bash executor's workers only.

Register the thread id as `native_session`; the native record proves the thread,
provider and model. Collection verifies the same thread settled and answered.

## Run a worker on a linked environment

A t3 route can name a linked environment (`t3 environment link <url> --pairing-code <code from `t3 pair`
there> --access <level>`, both directions): the worker's thread is then created and hosted on that
machine, and the lifecycle reaches it through that environment's T3 MCP server instead of the local CLI.
Start the thread there with `t3_thread_launch`, the startup probe as its `message`.
Cross-host calls are a beta: the environment serving them must enable `linkedEnvironmentsEnabled` (its
Settings → Labs); off, it refuses new links, calls over links and
tasks on another machine.

Choose the narrowest linked access that fits the job; the preflight checks the
route's access floor. A refusal does not authorize broader access.

The lifecycle's credential for a linked environment is the pairing credential that approved it: set
`T3_MCP_URL` and `T3_MCP_BEARER_TOKEN` for the session driving the route. The attempt's `native` record for
a remote thread is the `t3_thread_read` answer written in the same thread-state shape the local
`t3 thread show --json` writes (the nested `thread` beside `messages`) — write it at startup and rewrite it
before collection, exactly as the local flow does. A missing or refused credential
is a distinct refusal naming the fix (re-run `t3 pair` and re-approve the client). The local path — no
`environment` on the route — never needs a credential and is unchanged.

## Retire a worker

The `t3 thread` CLI has no stop command, and interrupting a run is an
MCP-only operation outside this route: under the
[retirement contract](../runtime/resources/retire.md) a T3 worker leaves when
its thread is archived, which hides it from the sidebar and keeps its history,
reversibly (the app's right-click menu, or `t3_thread_organize` with `action:
"archive"`). Never delete or cancel a user's thread: deleting is the user's
call, and it permanently clears the conversation and force-removes the
thread's git worktree. A retained thread takes its assignment's next attempt,
so a reviewer needed for a repair recheck stays unarchived until that phase ends.

Account for every owned thread as retained with its next use, or archived,
before returning. A finished parent's state does not establish its children's
retirement. Use lifecycle `status` and `retire` to verify closure; never archive a
thread the orchestrator does not own.
Interrupting a cross-host worker is `t3_thread_interrupt` on that environment's MCP
server. The call's arguments carry only the
thread id: the endpoint is addressed by `T3_MCP_URL`, never an `environmentId` on the wire (ledger A8).
One driving session holds one environment's `T3_MCP_URL`/credential: a route naming a different linked
environment needs its own driving session (a wrong endpoint refuses loudly on the thread check).
