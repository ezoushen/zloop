Load alongside the current host adapter when a `t3` route is selected. T3 Code
(https://github.com/pingdotgg/t3code) provides a transport: it launches and hosts
the worker; it does not replace the Claude, Codex, Pi or OpenCode host identity.
Read the installed `t3` CLI's help (`t3 thread start --help`, `t3 thread send
--help`, `t3 thread show --help`) before the first launch; it owns command
syntax. This file owns zloop coordination.

## Route before launching

T3 is a built-in executor type, but it has no ambient environment marker: unlike
Herdr's `HERDR_ENV=1`, nothing in the environment activates it. A configuration
layer selects it — a `t3` key in a runtime's `executors` map, or an agent entry
with `{"type": "t3"}` — and the resolver's preflight then verifies the
environment before any launch:

1. `~/.t3/userdata/server-runtime.json` exists (or the `T3CODE_HOME` the
   environment names) — "installed and has run here".
2. `t3 thread list --json --project <project-path>` exits 0 **and** its body
   parses as a JSON array (empty is fine: a registered project with no threads)
   — "the server is answering and the project is registered". Exit 1 means no
   server answers; exit 0 with a "No T3 Code project matches" message on stdout
   means the server is up but the project is not registered, so parse the body,
   never the exit code alone.
3. Never use `t3 status` or bare `t3 doctor` for liveness: both exit 0 when no
   service is installed while a desktop-app server is serving, and bare `t3
   doctor` repairs and restarts the service (`--dry-run` only, for diagnostics).

T3 can host the runtimes it supports among zloop's worker runtimes; a model
binding's `id` must be a model that provider accepts, and an unsupported
combination is refused with its reason. Do not infer support from a model name.
An MCP connection to the environment is a separate integration and is not part
of this route.

Inside a T3-spawned Pi thread (T3 injects `T3_MCP_URL`,
`T3_MCP_BEARER_TOKEN`, `T3_PI_RUNTIME_MODE` and `T3_PI_MCP_EXTENSION_PATH`;
the spawner strips inherited values, so presence means this session's own
credentials) a worker can recognize its own environment by those variables.
Never log the bearer token. Other providers get no such marker.

Pass the destination's host adapter to a cross-framework worker, plus this
guide. Use absolute paths for the adapter, agent and job files and verify their
reads succeeded before productive work.

## Start each worker in a thread of its own

1. Start the worker's thread in the project that contains the assigned
   worktree: `t3 thread start <project-path> <assignment> --title
   "zloop/<slug>/<assignment> <role>" --json`. The start message IS the
   assignment — the thread begins its turn immediately, so there is no separate
   submit step for the first prompt; later messages go through `t3 thread send`,
   which queues behind a busy turn and never interrupts. Adding
   `--worktree <base-branch>` makes T3 give the thread a worktree of its own; a
   read-only assignment runs in the project folder. The thread never runs in a
   zloop-assigned worktree path: the assigned worktree's identity is recorded in
   the registration and verified from the worker's report, not from the thread's
   directory. A new thread uses the project's default model and permission
   mode: verify the project's defaults allow unattended work at the assignment's
   scope before launching, and report a mismatch instead of proceeding.
2. Pass the model policy only through T3's `--provider` and `--model` flags:
   the binding's runtime maps to the T3 provider instance id (`pi`, `codex`,
   `claudeAgent`, `opencode`) and its `id` to the model slug that provider
   accepts, verified against the installed T3 before wiring. A pair the
   provider refuses is reported at launch with T3's own refusal; zloop does not
   approximate a slug.
3. Register the worker with `"t3": {"thread": "<thread id>"}` from the start
   response. Registration refuses a thread that does not exist, already holds
   another attempt, or whose state the CLI cannot confirm.

## Wait and recover

Register the attempt with `runtime: "t3"` and the thread id as `native_session`
(the identity is the thread, not a provider session record). At startup, write
`t3 thread show <thread> --json` to a file and record it as the attempt's
`native` record; **rewrite that file before collection** so the lifecycle reads
the settled status and the packet's reply from the current thread state.

Bind the prompt, independent wait and collected result to the registered attempt
under [worker attempts](../runtime/workers/prepare.md) and
[waits](../runtime/workers/wait.md). The first prompt was the start message;
a continuation submit on the local path is `t3 thread send <thread> <packet-text>
--wait`, whose text must be the registered packet. On a linked environment the
assignment rides the thread's start message (the `t3_thread_launch` message is
the packet — the live peer run's proven path); the MCP `t3_thread_send` tool is
reserved for continuations and is not yet routed by the lifecycle's submit path. Exit 0 prints the agent's reply; exit 2
means the agent is waiting for an answer in the app — that is the lifecycle's
waiting state, and the choice goes back to the orchestrator; exit 1 means the
run failed or stopped. `send` never interrupts: a busy thread queues the
message as its next turn.

Poll state only through `t3 thread show <thread> --json`; its status values
(preparing, queued, starting, running, waiting, completed, interrupted, failed,
cancelled) map to the lifecycle's vocabulary, `running` is working and
`waiting` is blocked-on-answer. After a timeout or a failed wait, inspect the
same thread with `t3 thread show` before waiting again or resubmitting;
neither a shell success message nor a timeout is completion, and a duplicate
send queues a second turn.

A T3 worker cannot prompt this orchestrator back (it can only message another
T3 thread), so the completion signal is the CLI wait itself, not a
worker-initiated push. Arm the lifecycle's wait on the `send`/`show`
combination and deliver receipts through the host's native channel.

## Sandbox stance and session identity

T3 spawns the provider itself, so zloop cannot wrap the worker's argv: a
T3-hosted worker runs under its provider's own defaults, unenforced by zloop
(the resolver's preflight and the thread's runtime mode are the controls). The
macOS Seatbelt profiles apply to the bash executor's workers only.

Register the thread id as the attempt's `native_session`: a T3 worker's identity
is its thread, not a provider session record. At startup, write the thread's
`t3 thread show --json` state to a file and pass it as the attempt's `native`
record; the lifecycle reads the model and status from it, and collection verifies
the same thread settled and answered.

## Run a worker on a linked environment

A t3 route can name a linked environment (`t3 environment link <url> --pairing-code <code from `t3 pair`
there> --access <level>`, both directions): the worker's thread is then created and hosted on that
machine, and the lifecycle reaches it through that environment's T3 MCP server instead of the local CLI.
Cross-host calls are a beta: the environment serving them must enable `linkedEnvironmentsEnabled` (app
Beta settings, or `t3_environment_preferences_update`); off, it refuses new links, calls over links and
tasks on another machine.

Access levels ceiling what agents may do there: `read-only` grants only the orchestration-read scope
(it cannot launch or send to a thread), `approval-required` and up grant orchestration operate, and
`full-access` additionally grants settings and source-control writes. The resolver refuses a route whose
worker's write scope exceeds the link's access (ledger A5 of the t3-cross-host workstream), naming the
ceiling. Choose the narrowest access that fits — `approval-required` for a review host.

The lifecycle's credential for a linked environment is the pairing credential that approved it: set
`T3_MCP_URL` and `T3_MCP_BEARER_TOKEN` for the session driving the route. The attempt's `native` record for
a remote thread is the `t3_thread_read` answer written in the same thread-state shape the local
`t3 thread show --json` writes (the nested `thread` beside `messages`) — write it at startup and rewrite it
before collection, exactly as the local flow does. A missing or refused credential
is a distinct refusal naming the fix (re-run `t3 pair` and re-approve the client). The local path — no
`environment` on the route — never needs a credential and behaves exactly as the single-host route in [Start each worker in a thread of its own](#start-each-worker-in-a-thread-of-its-own).

## Retire a worker

The `t3 thread` CLI has no stop command, and interrupting a run is an
MCP-only operation outside this route: retirement leaves the thread idle in the
project, with the registration handle cleared. Record that idle thread under
the [retirement contract](../runtime/resources/retire.md) as retained-by-design;
never delete or cancel a user's thread. An idle reviewer needed for a repair
recheck stays available until that phase ends.

Panel hygiene for retired threads is archive, not delete: archive hides the
thread from the sidebar while keeping its history, reversibly (the app's
right-click menu, or `t3_thread_organize` with `action: "archive"` over the
T3 MCP server). Deleting is the user's call, not a worker's: it permanently
clears the conversation and force-removes the thread's git worktree. Settled
threads auto-fade from lists after inactivity (7 days by default); note that
settling a parent thread does not settle its finished subagent threads
(upstream pingdotgg/t3code#33578), so archive each retired worker individually.
The lifecycle archives a retired thread on a linked environment itself
(`t3_thread_organize` on that environment); a local thread stays idle-retained
for the orchestrator to archive. Account for every owned thread as idle-retained
with its next use, archived after collection, before returning.
Interrupting a cross-host worker is `t3_thread_interrupt` on that environment's MCP
server — the same MCP-only rule the local retire section records. The call's arguments carry only the
thread id: the endpoint is addressed by `T3_MCP_URL`, never an `environmentId` on the wire (ledger A8).
One driving session holds one environment's `T3_MCP_URL`/credential: a route naming a different linked
environment needs its own driving session (a wrong endpoint refuses loudly on the thread check).
